# Оплата тарифов OimoQR через Finik

OimoQR использует Finik Web SDK как hosted payment flow: backend создаёт и подписывает платёж, пользователь переходит по выданной Finik HTTPS-ссылке, а оплаченный период включается только после проверки подписанного webhook.

Это **разовая предоплата**, а не автоматически возобновляемая подписка. Тариф на месяц или год нужно продлевать новым платежом. Интеграция работает только с тарифами в KGS и не хранит платёжные реквизиты пользователя.

Официальные материалы Finik:

- [Web SDK](https://www.finik.kg/documentation/web-sdk/);
- [интеграция и создание платежа](https://www.finik.kg/documentation/web-sdk/integration/);
- [webhooks](https://www.finik.kg/documentation/web-sdk/webhooks/);
- [адреса beta/prod и публичные ключи](https://www.finik.kg/documentation/web-sdk/reference/).

## 1. Как проходит оплата

1. Владелец выбирает опубликованный тариф с включённой онлайн-оплатой.
2. Frontend передаёт backend только внутренний `pricingTierId`. Сумму, валюту, период и ограничения backend берёт из БД.
3. Backend создаёт локальный `BillingPayment`, подписывает `POST /v1/payment` RSA-ключом продавца и получает hosted URL Finik.
4. Пользователь оплачивает счёт на странице Finik.
5. Finik отправляет подписанный webhook на `/api/billing/finik/webhook`.
6. Backend проверяет подпись, время запроса, `accountId`, скрытый одноразовый токен платежа, владельца, тариф и точную сумму, дедуплицирует событие и только затем включает или продлевает доступ.
7. Страница тарифа опрашивает локальный статус платежа. Возврат пользователя по redirect URL сам по себе оплату не подтверждает.

У Finik Web SDK нет используемого здесь browser SDK, Customer Portal и документированного автосписания. Источник истины — проверенный webhook, а повторное продление создаёт новый платёж.

## 2. Получите beta-доступ Finik

Для первого запуска запросите у Finik beta-реквизиты:

- `x-api-key` → `FINIK_API_KEY`;
- идентификатор счёта продавца → `FINIK_ACCOUNT_ID`;
- процедуру регистрации публичного RSA-ключа продавца;
- доступный способ проведения тестовой оплаты.

Beta API использует `https://beta.api.acquiring.averspay.kg`, production API — `https://api.acquiring.averspay.kg`. Адрес выбирается сервером через `FINIK_MODE=beta|prod`. Не смешивайте ключи, счёт и режимы разных сред.

Также заранее подготовьте публичный backend-домен с действующим TLS-сертификатом. Finik должен иметь возможность вызвать его из интернета; `localhost` не подходит.

## 3. Создайте RSA-ключ продавца

Сгенерируйте отдельную пару RSA-2048 для каждой среды:

```bash
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out finik_private.pem
openssl pkey -in finik_private.pem -pubout -out finik_public.pem
```

Зарегистрируйте содержимое `finik_public.pem` у Finik по выданной процедуре. `finik_private.pem` остаётся только у OimoQR и используется для подписи исходящих запросов. Никогда не отправляйте его во frontend, не добавляйте в Git и не вставляйте в тикеты или логи.

Публичный ключ Finik для проверки **входящих** webhook — другой ключ. Официальные beta/prod ключи уже встроены в backend. `FINIK_PUBLIC_KEY` нужен только как контролируемое переопределение, если Finik сообщит о ротации ключа; это не `finik_public.pem` продавца.

## 4. Настройте backend environment

Для beta добавьте в ignored-файл `backend/.env`:

```env
FINIK_MODE=beta
FINIK_API_KEY=replace-with-beta-api-key
FINIK_ACCOUNT_ID=replace-with-beta-account-id
FINIK_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----"
FINIK_PUBLIC_KEY=
FINIK_WEBHOOK_URL=https://staging-api.example.com/api/billing/finik/webhook
FINIK_MERCHANT_NAME=OimoQR
FINIK_PAYMENT_TTL_MINUTES=30
FINIK_SETTLEMENT_GRACE_MINUTES=1440
FINIK_WEBHOOK_TOLERANCE_SECONDS=300
FINIK_REQUEST_TIMEOUT_MS=10000
```

`FINIK_PRIVATE_KEY` хранится одной строкой с буквальными последовательностями `\n`; backend преобразует их в переводы строк. В Render вставьте значение тем же способом в Secret Environment Variable. Реальные ключи не должны появляться в `.env.example`.

Требования к переменным:

- `FINIK_WEBHOOK_URL` — абсолютный публичный HTTPS URL с точным path `/api/billing/finik/webhook`;
- `FINIK_PAYMENT_TTL_MINUTES` — локальное время жизни ссылки, минимум 5 минут;
- `FINIK_SETTLEMENT_GRACE_MINUTES` — защитное окно после истечения ссылки, в течение которого нельзя менять структуру аккаунта: валидный webhook мог быть доставлен с задержкой; по умолчанию 1440 минут;
- `FINIK_WEBHOOK_TOLERANCE_SECONDS` — допустимое расхождение timestamp webhook, минимум 30 секунд; значение по умолчанию 300;
- `FINIK_REQUEST_TIMEOUT_MS` — timeout обращения к Finik, минимум 1000 мс;
- `FINIK_PUBLIC_KEY` обычно оставляют пустым, чтобы использовать официальный ключ выбранной среды.

Finik-секреты нужны только backend. Переменных `VITE_FINIK_*` создавать не нужно.

### Webhook

Backend передаёт `FINIK_WEBHOOK_URL` Finik при создании каждого платежа. Endpoint публичный и расположен до общего rate limiter, однако любые изменения данных выполняются только после криптографической проверки запроса и привязки события к merchant account и локальному одноразовому токену платежа.

Не изменяйте path в reverse proxy и синхронизируйте системное время сервера: подпись включает HTTP path, host и timestamp. Повторная доставка одного webhook ожидаема и обрабатывается идемпотентно.

В документации Finik сокращённый пример payload не показывает `data`, но полный официальный пример проверки подписи содержит `data.accountId`. Backend намеренно требует совпадение этого merchant account вместе с `paymentId`, суммой и скрытым одноразовым токеном. Проверьте это поле на реальном beta webhook: при его отсутствии платёж безопасно попадёт в ручную проверку, а не активирует тариф. Не ослабляйте merchant-binding без письменного подтверждения контракта от Finik.

Согласно текущему контракту Finik, webhook сообщает об успешной оплате. Поэтому отменённая или брошенная оплата не активирует тариф и локально истечёт по TTL. Redirect обратно в OimoQR не является подтверждением платежа.

## 5. Обновите схему БД без потери данных

Сначала сделайте проверенный backup и прогоните обновление на копии production-БД.

Переход состоит из двух последовательных миграций:

1. `20261013120000_add_stripe_billing` — переходный слой первоначальной биллинговой схемы;
2. `20261014120000_replace_stripe_with_finik` — переименовывает Stripe-специфичные поля и таблицы в provider-neutral, сохраняет legacy-строки как `provider=STRIPE` и добавляет `BillingPayment` для Finik.

Вторая миграция предполагает, что структура первой уже существует. Важно: историческая migration chain этого репозитория не воспроизводит всю текущую Prisma-схему на пустой БД, потому что часть старых изменений применялась через `db push` и отдельные SQL-файлы. Поэтому до создания и проверки консолидированного baseline **не используйте текущий `migrate deploy` для новой staging/production-БД**. Для одноразовой локальной dev-БД допустим `prisma db push` без `--accept-data-loss`; это не создаёт production migration history.

### Существующая production-БД, ранее управляемая через `db push`

В проекте production исторически синхронизировался через `prisma db push`, поэтому фактическая схема может не совпадать с таблицей `_prisma_migrations`. Не запускайте `migrate deploy` вслепую и не отмечайте миграцию выполненной только ради устранения ошибки.

Перед deployment:

1. Снимите backup и временно остановите записи в биллинговые таблицы.
2. Сравните реальную схему, `_prisma_migrations` и обе SQL-миграции.
3. Подготовьте и протестируйте консолидированный baseline текущей production-схемы либо явно reconcile каждую историческую миграцию. `prisma migrate resolve --applied ...` допустим только после проверки, что соответствующие изменения уже полностью присутствуют в БД.
4. Если структура `20261013120000_add_stripe_billing` уже присутствует, но запись отсутствует в `_prisma_migrations`, сначала проверьте все её объекты и только затем выполните `npx prisma migrate resolve --applied 20261013120000_add_stripe_billing`.
5. Примените `20261014120000_replace_stripe_with_finik` через проверенный migration step. Миграция обёрнута в PostgreSQL-транзакцию. Если SQL пришлось применить вручную, после полной проверки результата обязательно зарегистрируйте его командой `npx prisma migrate resolve --applied 20261014120000_replace_stripe_with_finik`, иначе следующий `migrate deploy` попытается повторить rename.
6. Выполните `npx prisma migrate status`, schema diff и сверку количества/содержимого billing-строк на копии БД.
7. Только после успешной проверки примените тот же план к production, затем разверните код и выполните smoke test.

`prisma db push` не обязан распознать rename и может предложить удалить старые колонки или таблицы и создать новые. Не используйте `--accept-data-loss`. Текущий `render.yaml` намеренно выполняет только `prisma generate` и не меняет production-БД во время build. Примените проверенный baseline/migration отдельным контролируемым шагом до deployment; после нормализации истории можно осознанно добавить `prisma migrate deploy` в release pipeline.

Считайте миграцию обязательным release gate: новый backend нельзя запускать поверх старой схемы, даже если Render build завершился успешно.

Если состояние production-схемы отличается от обоих ожидаемых вариантов, остановитесь и подготовьте отдельный SQL-план на основе schema diff; не угадывайте имена уже существующих объектов.

## 6. Настройте тарифы

В административной странице тарифа:

1. Укажите цену больше нуля.
2. Выберите валюту `KGS`.
3. Выберите период `month` или `year`.
4. Проверьте тип бизнеса и максимальное число ресторанов.
5. Включите онлайн-оплату и опубликуйте тариф.

Finik получает сумму с backend, а не из браузера. После появления платежей цена, валюта, период и ограничения тарифа защищены от изменения; для новой цены безопаснее создать новый тариф и отключить старый для новых продаж.

При успешной оплате месячный или годовой период применяется ко всем ресторанам владельца. Повторная оплата того же тарифа до окончания доступа продлевает срок от текущей даты окончания. Переход на другой тариф во время активного оплаченного периода автоматически не выполняется.

### Ручная проверка спорного webhook

Каждый криптографически проверенный webhook сохраняется в неизменяемом `BillingWebhookEvent` вместе с payload, подписью и timestamp. Очередь администратора доступна через `GET /api/admin/billing-issues`.

- `POST /api/admin/billing-issues/:id/reconcile` повторно применяет только событие, которое проходит все финансовые проверки.
- `POST /api/admin/billing-issues/:id/resolve` с `{ "decision": "KEEP_CURRENT_STATE", "note": "..." }` закрывает аномалию уже подтверждённого `PAID` ledger или orphan-событие без изменения доступа.
- Тот же endpoint с `{ "decision": "REJECT_UNAPPLIED_PAYMENT", "note": "..." }` переводит неприменённую попытку в `FAILED`. Комментарий администратора обязателен и сохраняется в issue.

`PAID` ledger нельзя отклонить этим endpoint, а неприменённый платёж нельзя закрыть как `KEEP_CURRENT_STATE`; такие ограничения не дают скрыть недоплату или случайно отозвать уже выданный период.

## 7. Проверьте beta end-to-end

Запустите backend с beta credentials и публичным HTTPS webhook. Затем:

1. Включите онлайн-оплату только у тестового KGS-тарифа.
2. Создайте платёж со страницы тарифов и убедитесь, что открывается HTTPS-страница Finik.
3. Проведите оплату способом, выданным Finik для beta.
4. Убедитесь, что один redirect без webhook не активирует доступ.
5. После webhook проверьте статус `PAID`, даты периода и права всех ресторанов владельца.
6. Повторно доставьте тот же webhook и убедитесь, что период не начислился дважды.
7. Проверьте истечение неоплаченной ссылки и повторное создание платежа.
8. Проведите повторную оплату того же тарифа и проверьте корректное продление периода.

Frontend опрашивает локальный `GET /api/billing/payments/:paymentId`; это не запрос статуса в Finik. Если подписанный webhook не пришёл, доступ не выдаётся — сначала проверяйте TLS, точный URL, время сервера и логи проверки подписи.

Платёж с несовпадающей суммой, неизвестным тарифом или нарушенными ограничениями не применяется автоматически и попадает в очередь:

```text
GET  /api/admin/billing-issues
POST /api/admin/billing-issues/:id/reconcile
```

Исправьте причину и только затем повторяйте reconcile. Автоматический refund/cancel flow не реализован; возврат выполняйте по согласованной с Finik процедуре и отражайте решение в OimoQR вручную.

## 8. Перейдите в production

Перед включением реальных платежей:

1. Получите отдельные production `x-api-key`, `accountId` и зарегистрируйте отдельный публичный RSA-ключ.
2. Установите `FINIK_MODE=prod` и замените все beta credentials на production credentials.
3. Укажите production URL `https://<backend-domain>/api/billing/finik/webhook`.
4. Убедитесь, что серверное время синхронизировано, TLS-цепочка действительна, а proxy сохраняет host/path.
5. Проведите реальную минимальную оплату и сверьте сумму, webhook, срок доступа и идемпотентность.
6. Настройте мониторинг ошибок создания платежей, отклонённых webhook и открытых `BillingIssue`.

Private key, `x-api-key` и содержимое подписываемого запроса с чувствительными заголовками не логируются и не передаются в браузер. При подозрении на утечку отзовите API/RSA credentials у Finik, выпустите новую пару и обновите Render secrets.
